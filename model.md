# Experience-based travel decisions

This document defines the accepted learning contract for the river-city expansion. The selected approach is a small persisted tabular action-value model using outcomes generated inside the fictional simulation. It is not a trained neural network, LLM, external AI service, real-world predictor or a claim that every NPC learns every possible pattern. Canonical fields and update logic live with the simulation; completion and evaluation evidence belong in status.md.

## Data and decisions

Inputs are simulated source/destination access, route distance and available transport. The context is `crossing` for opposite river banks, otherwise `long` for a Manhattan route distance greater than five map units or `local`. Actions are porter/cart/barge transport choices. Porter and cart are eligible for ordinary deliveries; barge is eligible only for an unfrozen cross-river dock-to-dock trip. An action cannot invent roads, stock, money, capacity or a building type absent from the model. Resource conservation, task persistence, load eligibility and valid lifecycle transitions remain explicit rules.

An observation is an actual completed delivery. Its duration runs from the shipment's creation tick to completion, including approach, interruptions, handling and queue time. The model does not learn from a decorative animation, its own prediction, or a merely assigned journey. Pending shipments retain identity across interruptions and saves. Stranded shipments that are recovered eventually contribute their full elapsed cost; incomplete/cancelled journeys do not currently produce a negative reward update. Consequently, failure rates must be evaluated separately rather than assuming the table learned to prevent every failed trip.

`world.learning` holds at most nine `context:mode` entries, each containing `samples`, `meanDuration`, `meanAmount` and `value`. Duration is measured in simulation ticks (ten fictional minutes each). A completed shipment of amount `a` taking `d = max(1, completedTick - createdTick)` yields reward `a / d`. The sample count increments; duration/load means use incremental sample averages; the action value updates as `value += 0.2 * (reward - value)`.

An unseen eligible mode is selected first in explicit porter/cart/barge order. Once eligible modes have samples, selection maximizes `value + 0.15 * sqrt(log(totalSamples + 1) / samples)`, with deterministic mode order breaking ties. This is a small upper-confidence exploration policy over tabular action values, not deep reinforcement learning. Dispatch also compares candidate sources/requests using distance, approach, urgency, amount and learned mean duration per unit. Without experience it uses the modeled distance/speed/capacity estimate. Unavailable actions are masked regardless of their learned value.

## Persistence and trust boundaries

Schema 3 persists the shared `world.learning` table, lifetime delivery totals, each person's `experience: { deliveries, meanTrip }` and pending shipment/job identities. `meanTrip` is an incremental mean of completed duration in simulation ticks; it reports experience rather than controlling a separate personal neural policy. Export/import must preserve future choices for the same saved state and seed. Schema-2 imports are validated against their original contract in `colony-v2.js` before migration initializes an empty table and the new cargo/ledger fields; the game does not pretend that the old world already accumulated experience. Previously paid construction materials are accounted on-site during this migration. Unknown fields, invalid contexts/actions, nonfinite estimates, impossible counts, oversized tables and broken pending-job references are rejected before world replacement.

All data is locally generated fictional simulation state. No personal datasets, user browsing history, remote training corpus, credentials or inference provider are required. World exports remain local unless the user intentionally shares them. The ordinary single-file game should continue without a model download or external service.

## Evaluation and interpretation

Required correctness checks are deterministic updates, bounded/finite values, valid-action masking, no duplicate outcome counting, save continuation and legacy migration. The implementation/correctness evidence does not establish policy superiority: comparative outcome evaluation remains separate and must be recorded in status.md before making an improvement claim. Compare the learned selector with the same transparent baseline on multiple seeded worlds, including seeds not used to tune cost/reward definitions. Measure delivered throughput, journey/queue time, failed/stalled work and survival/resource outcomes. More buildings alone is not a sufficient objective. Report both improvements and regressions; a table that updates is implementation evidence, not proof that decisions improve.

Long-run evaluation must include shortages, blocked/closed routes, winter river navigation, varying population and recovery after interrupted work. A policy that favors short trips while starving a critical distant project is a failure even if its average travel cost falls. Keep physical constraints and a usable fallback outside the learned preference. This model is deliberately modest: no optimality, general intelligence, calibrated forecasting or transfer to real cities is claimed.

Detailed banking contagion and contextual-bandit interest-rate policies are deferred. They require an independently functioning firm/credit ledger, delayed repayment outcomes and a meaningful baseline before learning can be assessed. They are not implicit consequences of adding this travel experience table.
